## Supported-boundary design

For first adapter support, designate existing architecture source artifacts from the exact current r3 format and existing baseline COMMON_RESULT only after its distinct native mode/core proof is actually supported. Native evidence has no architecture reservation/settlement witness format; do not invent one to get A. A legacy-valid baseline can remain S under stricter observations if its own source verifier passes; lack of support yields lower capture or actual typed failure, never false eligibility. Old v1/r2 artifact formats and arbitrary consumers remain outside initial supported profiles; their sources/bytes remain unchanged.

Introduce new observation_v21.adapter.observe_run_v21/read_outcome_v21 only after separate authorization. Consumers explicitly choose it and route schema_version+contract_version before any projection. Legacy normal readers must reject any new schema/variant tag, reject current hold diagnostic as normal, and verify archived legacy positives with the original full verifier. Never overwrite old files with new tags. An outer/embedded result/C0/FINAL fragment is forbidden in the new envelope; arbitrary noncompliant readers have no broad compatibility guarantee.

## Thirty-cell retained matrix

Retain the exact six APIs × five original evidence/reason columns from prior V2_R4_API_REVIEW.md: VERIFIED, BLOCKED, INTERRUPTED, UNKNOWN, INVALID_RESPONSE. These are30 cases, not a five-state provenance enum. Each future cell must record direct return/exception type/cause, side effects, source bytes, dispatch count and expected field availability. Verified uses a real valid positive; BLOCKED uses actual corruption and cannot pass from any generic exception; UNKNOWN remains charged unknown usage, not fake zero; interrupted has valid restricted/C0 recovery; invalid response is orthogonal to provenance and never semantic answer success.

Add14 reader/error vectors: archived normal positive; current normal positive; current hold reject-as-normal; three opted-in variants; missing version; unknown version; mixed tags; forged legacy fields; generic I/O; ordinary RuntimeError; missing/corrupt ledger; forged hold/report. Missing/corrupt ledger may be parameterized further without weakening both subcases. Add8 source-mode/candidate-boundary vectors: architecture/baseline valid, their unsupported format counterparts, valid C0 with later unknown cost, missing candidate, rebound handle, source-valid S. Total planning allocation E=52 named vectors; parameterized subcase count must be recorded by the eventual runner, not assumed from these budget groups.

No broad catch is allowed. A valid grounded F02 rejection may feed the separate new diagnostic route, and a failed snapshot can ground UNKNOWN only under the accepted cause rules. Diagnostic storage failure, unrelated integrity failure, unsupported source semantics and programming errors remain actual failures. Future acceptance requires all designated old consumers observe unchanged legacy behavior and all new consumers receive only validated opted-in values.
