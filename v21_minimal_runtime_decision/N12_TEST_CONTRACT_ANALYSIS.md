# N12 diagnostic contract analysis — no execution or rescore

Historical N12 remains **FAIL**, control exit1; its evidence child exited0 after recording write denial. Path.write_bytes(`wb`) returned PermissionError, errno13, winerror=null. The assertion required winerror==5, so later unchanged-byte/post-release/core assertions were not reached. A separate post-failure read-only receipt found unchanged wire SHA and post-exit access, but did not make N12 pass. All original code/results are preserved.

## Evidence-backed equivalence limit

The operation was an attempted truncating write to an existing journal while a parent native read handle allowed FILE_SHARE_READ only. It was **not** the earlier Ledger.register os.replace operation that exposed WinError5. CPython 3.12 FileIO uses `_wopen` and constructs the failure from errno; that route can omit a native WinError field. This is a published 3.12 source-path explanation, not a bit-for-bit attestation of the bundled interpreter build. [CPython FileIO source](https://raw.githubusercontent.com/python/cpython/3.12/Modules/_io/fileio.c).

Microsoft documents EACCES from `_wopen` for sharing-mode denial as well as read-only/path cases. Thus errno13 can be consistent with the intended denial, but does not distinguish its cause. [Microsoft CRT _open/_wopen](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/open-wopen?view=msvc-170).

Win32 ERROR_ACCESS_DENIED is5; ERROR_SHARING_VIOLATION is32. CreateFile sharing conflicts have their own native error semantics. They are not numerically interchangeable with CRT errno13, and the historical native cause was not recorded. Do not infer it later with GetLastError or equate exceptions merely because both are PermissionError. [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [Win32 error codes](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--0-499-).

Conclusion: errno13/winerror=null is compatible with this operation's expected access denial, but the saved event alone does not prove it is specifically WinError5 or uniquely caused by the held pin. The source and unchanged/post-access evidence support that causal interpretation, not a recovered native code. No further broad feasibility exercise is needed; specify and implement a versioned meaningful-operation test later.

## Proposed new test N12-v2, separately authorizable

Use fresh synthetic NTFS files only, save exact script/source hashes and before bytes/file IDs. Predeclare phase markers, API flags, errors and bounds. First show the same writer's access succeeds without the pin on a separate matched control file (or the exact target with explicit restoration before baseline), and verify target is a regular writable file, not missing/read-only/reparse/directory. No privilege/sandbox exception is counted as native success.

Parent acquires the existing GENERIC_READ/FILE_SHARE_READ/OPEN_EXISTING pin and records native handle/file identity. Only then release a ready child to attempt the original Path.write_bytes operation. Preserve Python exception type, errno, optional winerror, exact target, PID/start identity, flags and phase; compare them to the expected mapped denial rather than requiring an unavailable winerror property.

Also make a **separate directly recorded native CreateFileW probe** using GENERIC_WRITE, share READ|WRITE|DELETE, OPEN_EXISTING and FILE_ATTRIBUTE_NORMAL against the same parent read-only-share pin, and capture GetLastError immediately on failure before any other API. This probe requests write access without truncating bytes. For that precisely specified sharing-conflict probe require documented ERROR_SHARING_VIOLATION32. A native ACCESS_DENIED5 alone is not automatic proof of a pin cause; classify it as unexpected/insufficient for that assertion and retain it. Do not manufacture a mapping from Python errno after the fact. Native/Python probes are distinct observed operations, never claimed to be one syscall.

Require readiness before action, denial while the pin is actually held, exact unchanged bytes/content/file identity, no candidate/ledger changes, joined child/exits, closed owned pin handles, and the original writer/access succeeding after release on scratch. Preserve pre/post control data. If truncation unexpectedly succeeds, retain the preimage and actual damaged scratch bytes and FAIL. No exception-name-only PASS, blanket catch, timeout-to-PASS or discarded unknown event. Record observed_event, expected_event, elapsed_time, bound_satisfied, control_verdict and feasibility_implication separately.

Proposed fixed bounds: readiness5 seconds, each action3 seconds after its release marker, cleanup/join3 seconds and overall worker watchdog12 seconds; existing capture guard ceiling5 seconds/at most2 acquisitions is unchanged. Record the watchdog trigger and cleanup separately. These are prospective bounds, not new measured results. Unknown error, missed deadline/marker, resource leak or wrong diagnostic is FAIL. The new result is separate from old N12 regardless of outcome. It tests existing-file denial only; it cannot establish namespace exclusion, all-writer enrollment, safe reentrancy, A/S or actual inference.
